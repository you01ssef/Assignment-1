My Website Threat Model

What could go wrong with my portfolio, what needs protecting, and how I would reduce the risks using STRIDE.

Site architectureExplore STRIDEProtection plan

What am I protecting?

Content integrity

Keep my portfolio accurate and prevent unauthorized changes.

Account & privacy

Protect my GitHub publishing access and avoid exposing sensitive information.

Availability

Keep the website and its interactive features usable for visitors.

How this website works

02 / CLIENTWeb browserRuns the JavaScript application

03 / HOSTGitHub PagesServes website files over HTTPS

Publishing: Website owner → GitHub sign-in → repository → GitHub Pages.

Current scope: This is a static website. The chatbot uses predefined answers in the browser. There is no database, visitor login, or external AI API in the reviewed code. The browser also requests fonts from Google Fonts.

Trust boundaries: visitor input enters the page; files travel from the host to the browser; GitHub permissions control publishing; font requests reach a third party. Public viewing is allowed, but publishing changes requires authorization.

Six ways to think about threats

STRIDE groups threats into six categories. These are potential scenarios and suggested priorities, not claims that an attack has happened or that the listed controls are already enabled.

SHigh priority

Spoofing

Authentication & credential attacks

Someone uses a phished password or stolen GitHub session to impersonate me and publish a fake portfolio.

How I would reduce the risk

Use a passkey or strong MFA, unique credentials, and review active sessions.

THigh priority

Tampering

Unauthorized changes

Someone with stolen or excessive repository access alters the website or inserts malicious links.

How I would reduce the risk

Restrict write access, review changes before publishing, and keep a known-good version.

RMedium priority

Repudiation

Denying an action

A contributor denies making an unwanted change, making investigation harder, especially with shared accounts.

How I would reduce the risk

Use individual accounts and retain commit and deployment history. Commit metadata alone does not prove who controlled an account.

IHigh priority

Information Disclosure

Data leakage & XSS

Private information or credentials could be exposed in public files. The chatbot also inserts visitor messages as HTML, creating an injection risk in that visitor’s page.

How I would reduce the risk

Keep secrets out of public files and display visitor messages as plain text. A cross-user chat exploit has not been demonstrated.

DMedium priority

Denial of Service

Loss of availability

Heavy traffic could disrupt hosting. Separately, very large or repeated chat messages could slow a visitor’s browser.

How I would reduce the risk

Monitor availability and use host protections. Cap chat message length and history; browser limits do not protect the hosting service.

EHigh priority

Elevation of Privilege

Authorization & unauthorized access

An overly broad collaborator role or deployment token gives someone more publishing access than they need.

How I would reduce the risk

Apply least privilege, remove unused access, and restrict deployment-token permissions.

Two important scope notes

SQL INJECTION

No database, no SQL queries

SQL injection does not apply to this version because it does not use a database. If I later store accounts or messages, I would use parameterized queries and restrict database permissions.

AUTHENTICATION

The 2FA widget is a demo

The widget generates and checks a number inside the browser. It does not implement real time-based authentication or protect private resources. Any future login and access checks must be enforced on a server.

My protection plan

  1. Handle chat input safely. Render visitor messages with textContent instead of innerHTML, then verify that HTML-like text stays literal.
  2. Secure publishing access. Review GitHub MFA, collaborators, sessions, and token permissions. Keep credentials out of website files and repository history.
  3. Keep the site usable and recoverable. Limit chat input and message history, retain a known-good version, and check deployment records after unexpected changes.

Assessment based on the portfolio source. Account settings have not been audited, and these improvements are a plan. I will revisit the model if I add accounts, a database, or an AI service.
