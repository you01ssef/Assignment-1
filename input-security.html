Controlled security lesson

Treat input as data.

A harmless, local demonstration of how unsafe SQL string building changes a query—and how validation and prepared statements address different parts of the problem.

What can go wrong?

If an application joins a username into SQL text, quotes and operators in the input can change the query’s meaning. The example is illustrative only: this page never opens a database or runs the displayed SQL.

Vulnerable pattern

const sql = "SELECT id FROM users WHERE username = '" + username + "'";
db.exec(sql);

Input becomes part of the SQL program. Hand-written escaping is fragile.

Secure pattern

const statement = db.prepare(
  "SELECT id FROM users WHERE username = ?"
);
statement.get(username);

The database receives query and value separately. The value stays data.

Three defenses with separate jobs

  1. Validate input. Check type, length, and allowed format at the application boundary. Reject invalid values early; validation does not neutralize SQL metacharacters.
  2. Use parameterized queries. Keep SQL structure fixed and bind input as a parameter. Never concatenate untrusted values into query text.
  3. Limit database access. Use a least-privilege database account, authorize each record by its owner, and avoid exposing database errors or secrets to the browser.

The optional Express/SQLite backend checks username and password formats, uses prepared statements with placeholders, and includes the authenticated user ID in note lookups and deletes.
