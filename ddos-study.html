01 / THE PROBLEM

Can data reveal abnormal traffic?

Can a combination of flow duration, packet counts, byte counts, and timing distinguish labeled DDoS traffic from benign traffic more effectively than a high packet-rate rule in the Friday afternoon CICIDS2017 capture?

The objectives are to compare normal and attack traffic, evaluate an interpretable detector on held-out feature profiles, and explain how false alarms and missed attacks affect website availability.

Finding: the decision tree achieved 0.9980 F1 on this single-capture test, while a high-rate rule missed nearly every attack. High per-flow packet rate alone was a poor signal here. This is a benchmark result, not evidence of production readiness.

DoS: one attack source

A denial-of-service attack exhausts resources such as bandwidth, connections, or application capacity, preventing legitimate access. A single source can cause denial of service; some attacks work slowly rather than sending a large flood.

DDoS: distributed sources

A distributed denial-of-service attack coordinates traffic from multiple sources. Blocking one source may be insufficient. Both attack types threaten availability; this experiment evaluates the dataset’s DDoS label, not the separate DoS variants.

02 / THE EVIDENCE

A public network-flow dataset

CICIDS2017 — Friday afternoon DDoS capture. Downloaded from San0160’s Hugging Face mirror. The original dataset is from the Canadian Institute for Cybersecurity, University of New Brunswick. The original collection took place in a controlled network in July 2017; Friday includes a DDoS scenario.

A row summarizes a bidirectional network flow, not a website visit or an individual packet. BENIGN is the normal class (0); DDoS is the attack class (1). The raw file contains 97,718 benign and 128,027 DDoS rows. This subset does not represent the frequency of attacks on the public Internet.

1. Normal traffic

Benign flows have a median of 6 packets and 248 bytes here. Legitimate traffic varies considerably, including very short flows with large calculated packet rates. A universal “normal” rate cannot be inferred from this capture.

2. Attack traffic

DDoS flows have a median of 8 packets, 11,627 bytes, and a longer duration. Their median packet length is 833.5 bytes, versus 61 for benign flows. These are associations in this scenario, not rules for all DDoS attacks.

3. Traffic volume

The attack class has more flows and more total bytes, but fewer total packets. Its median per-flow packet rate is lower: 2.59 versus 27.48 packets/s. Summing flow rates would not estimate concurrent network throughput.

4. Attack patterns

Duration, packet sizes, direction counts, and inter-arrival times together can separate this scenario better than a single threshold. This CSV lacks timestamps and source identities, so we cannot reconstruct synchronized bursts or count attacking hosts.

5. Abnormal behavior

Establish a baseline for each service and time window, then investigate deviations in volume, connection completion, latency, and source diversity. Here, a training-benign 99th-percentile rate threshold is a deliberately simple baseline; its failure shows why context matters.

6. Detection methods

Statistical thresholds are interpretable but may miss attacks. Anomaly detection can flag departures from normal behavior without known attack labels. Supervised learning combines labeled signals; the decision tree below is our implemented approach. An anomaly model is a future comparison, not an experiment run here.

04 / EXPERIMENT DESIGN

Preprocess, group, then evaluate.

  1. Validate: strip whitespace from column names and labels; convert the eight selected columns to numbers; remove 36 rows with missing, infinite, or negative selected values. No rows are removed for being extreme but finite. Keep 97,684 benign and 128,025 attack records.
  2. Prevent exact-profile leakage: group by all eight selected values, without the label. There are 16,397 repeated profiles beyond the first occurrence, and 24 groups contain conflicting labels. Retain them, keeping each group in one split.
  3. Hold out data: use the first fold of a shuffled, stratified, five-fold grouped splitter (seed 42): 180,443 training rows and 45,266 test rows. This is one evaluation split, not five-fold cross-validation.
  4. Fit on training only: the baseline flags rates above 666,666.6667 packets/s, the benign training 99th percentile. The tree has maximum depth 5, minimum leaf size 50, balanced class weights, and seed 42. Scaling and imputation are unnecessary after the stated cleaning.
  5. Evaluate once: use the tree’s default predicted class, with no test-set threshold tuning or parameter search. Report attack precision, recall, F1, false-positive rate, and confusion counts. EDA covers the cleaned capture and is descriptive.

Precision measures how many flagged flows are attacks; recall measures how many attacks are found; F1 balances the two. The tree detected 99.805% of labeled attacks, while 0.270% of benign test flows triggered false alarms. The rate rule detected only 2 attacks and raised 211 false alarms.

High benchmark scores are plausible because records share a controlled capture scenario. Grouping removes exact selected-profile overlap, but not correlations between related flows, hosts, or attack sessions. The result supports combining features within this dataset; it does not prove generalization to unseen campaigns.

06 / FROM DETECTION TO DEFENSE

Detection helps protect availability.

Early alerts can support analyst review and carefully scoped rate limits, filtering, caching, or upstream DDoS mitigation before application capacity is exhausted. Monitor legitimate-user latency, errors, and resource pressure alongside alerts, and verify recovery after any change.

False negatives let malicious traffic continue consuming capacity. False positives may deny legitimate users access—the same availability problem the defense is intended to prevent. A model should inform a measured response, with review, rollback, and protection for legitimate traffic.

Conclusions and limitations

Yes, data-driven methods distinguish labeled DDoS flows in this experiment. The shallow tree substantially outperformed the rate-only rule. However, this is historical, single-scenario data; labels and flow extraction can contain artifacts; the class mix is unlike many real deployments; and correlated flows can inflate scores. This file provides neither website uptime nor response times, so no improvement in availability was measured.

Future improvements

  • Evaluate on different days, networks, and recent attack families, including low-rate DoS, with host/session/time-separated splits where metadata permits.
  • Compare anomaly detectors and calibrate thresholds using a separate validation set and realistic attack prevalence.
  • Measure false alarms per hour, detection delay, and legitimate-user response times in an authorized lab before considering automatic mitigation.

Scope: this project downloads public records and performs offline analysis. It does not launch attacks or send test traffic to websites.
