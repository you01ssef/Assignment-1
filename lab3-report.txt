ARP and Ethernet answers

The expected sequence after clearing a gateway entry is an ARP broadcast request, a usually unicast ARP reply, then ICMP Echo Requests and Echo Replies. Background traffic may also appear.

Broadcast destination: ff:ff:ff:ff:ff:ff.

Ethernet field order: destination MAC first, source MAC second, then EtherType for an untagged Ethernet II frame. ARP uses 0x0806; IPv4 uses 0x0800. VLAN tags can add fields; the frame check sequence is often omitted by capture hardware.

ARP fields: hardware type, protocol type, hardware address length, protocol address length, opcode, sender hardware address, sender protocol address, target hardware address, and target protocol address.

Do all fields have data? They occupy space in the packet, but a request’s target hardware address is unknown and is commonly all zeroes. That is different from the Ethernet broadcast destination.

For Ethernet/IPv4 ARP, hardware type is 1, protocol type is 0x0800, hardware length is 6, and protocol length is 4. The reply provides the gateway’s hardware address so the client can send its frame to that address. See RFC 826.


Ping protocol: Wireshark lists ICMP for IPv4 ping; Echo Request is type 8/code 0 and Echo Reply is type 0/code 0. The display filter arp shows only ARP; icmp shows the IPv4 ping exchange.


DNS over UDP and Telnet over TCP

Illustrative field values only. Checksums are invented examples, not validated against packet bytes.

Reply ports reverse direction. Client ports and checksums vary between runs. DNS can also use TCP; this scenario uses ordinary UDP DNS. No real kean.edu address or Telnet service availability is asserted.


Header comparison: UDP has an 8-byte header with source port, destination port, length, and checksum. TCP has a minimum 20-byte header and adds sequence and acknowledgment numbers, header length, control flags, a receive window, and an urgent pointer; options can extend it. TCP supports reliable, ordered delivery, retransmission, flow control, and congestion control. UDP does not supply those guarantees. See RFC 768 and RFC 9293.

Meaning of /etc/passwd: Each colon-separated entry contains username, password marker, numeric user ID, numeric group ID, descriptive information, home directory, and login shell. An x commonly indicates a password hash stored separately in /etc/shadow. The file is an account directory, not a list of plaintext passwords. No real account listing is reproduced here.

Permissions: 0755 means the owner may read, write, and execute; group and others may read and execute. On directories, execute permits traversal. The handout also requests 0755 for referenced files; static HTML commonly needs only 0644 when server policy allows it.

Simulated server response: “Message accepted for delivery” is an illustrative success response, not output from obi2. Some mail clients simply return to the shell with no confirmation; submission does not prove inbox delivery. The local mail command and period/EOF behavior vary by implementation.

Possible exploitation: A misleading From address can impersonate a trusted sender in phishing or social-engineering messages. A mail system may reject or rewrite the alternate sender instead of accepting it.

Can the true sender be found? Trusted Received headers can help trace servers, and Authentication-Results can show SPF, DKIM, and DMARC outcomes. These checks help establish domain authorization and message integrity; they do not conclusively identify a human. Lower, attacker-supplied headers may be forged. Server logs and authorized investigation may be needed.

Protocol roles: SMTP sends mail between servers, commonly over TCP 25. POP3 retrieves messages, conventionally on TCP 110; IMAP synchronizes mailbox access, conventionally on TCP 143. TLS-enabled alternatives commonly use 995 and 993. This handout does not actually include a POP3 packet-capture exercise. An SSH client capture of a remote mail command shows SSH, not necessarily the remote server’s SMTP exchange.

DISCUSSIONProblems, fixes, and takeaway.

Actual limitation: No packet capture or authenticated university session was available for this report. The response was to prepare the explanations, webpage artifact, and explicitly simulated observations. The hands-on work remains unverified.

ARP request missing: An entry may be cached, the wrong interface may be selected, or the traffic may use IPv6 neighbor discovery. Verify the interface, address family, and cache state before repeating the authorized test.

Telnet unavailable: Service restrictions or off-campus access may prevent connection. Record the actual error and ask the instructor about an approved alternative; an SSH connection is not proof of a Telnet capture.

Checksum flagged: Outgoing checksum offloading can make a local capture appear to contain an incomplete checksum. Do not immediately interpret that as packet corruption.

Webpage not loading: Check the exact public_html path, lowercase index.html name, case-sensitive links, and the assigned permissions.

No FTP or HTTP label: SFTP and HTTPS encrypt application content. Filter the relevant connection and inspect SSH/TLS rather than expecting plaintext.

Email behavior differs: The server may reject sender overrides or the mail command may use different syntax. Record actual output rather than assuming successful delivery.

Conclusion: ARP resolves a local IPv4 neighbor’s link-layer address; ICMP supports reachability diagnostics; UDP minimizes transport overhead; TCP supplies a reliable byte stream. SSH and TLS protect application traffic, while email sender fields must be assessed alongside authentication and trusted routing evidence.
